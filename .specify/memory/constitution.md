# Stock Management Constitution

## Core Principles

### I. 코드 품질 (Code Quality)

- 모든 코드는 머지 전에 프로젝트 표준 린터와 포매터를 **경고 0건**으로 통과해야 한다(MUST).
  린트 규칙을 끄는 인라인 주석은 사유를 함께 적어야 한다(MUST).
- 함수의 순환 복잡도(cyclomatic complexity)는 10 이하, 함수 본문은 50줄 이하여야 한다(MUST).
  초과가 불가피하면 PR 설명에 근거를 남긴다.
- 도메인 로직(평가손익·수익률·등락 계산, 가이드 사용 한도 판정 등)은 UI·전송 계층·영속성 계층과 분리된 순수
  모듈에 둔다(MUST). 계층 간 의존은 한 방향(표현 → 애플리케이션 → 도메인)으로만 흐른다.
- 수량과 금액(평단가, 현재가, 손익)은 부동소수점 타입으로 다루지 않는다(MUST). 통화별 정밀도
  (예: KRW 원 단위 정수, USD 소수 자리)를 지키는 정수 최소 단위 또는 고정 소수 타입을 사용한다.
- 외부 입력(사용자 입력, API 요청, 외부 연동 응답)은 경계에서 검증한다(MUST). 내부 코드는
  검증된 타입을 신뢰하고 같은 검증을 반복하지 않는다.
- 오류는 삼키지 않는다(MUST). 처리하거나, 맥락을 붙여 상위로 전달하거나, 사용자에게 의미 있는
  메시지로 노출한다. 빈 catch 블록은 금지한다.
- 죽은 코드, 주석 처리된 코드, 사용하지 않는 의존성은 커밋하지 않는다(MUST).
- 새 추상화나 의존성은 현재 요구사항이 필요로 할 때만 도입한다(SHOULD, YAGNI).

**근거**: 평단가·수량·손익 계산의 오류는 사용자의 투자 판단 오류로 이어진다. 복잡도 상한과 계층 분리는
도메인 규칙을 테스트하고 리뷰할 수 있는 크기로 유지하기 위한 장치다.

### II. 테스트 표준 (Testing Standards, NON-NEGOTIABLE)

- 기능 구현과 버그 수정은 테스트 우선(Red → Green → Refactor)으로 진행한다(MUST). 버그 수정은
  해당 버그를 재현하는 실패 테스트를 먼저 추가한다.
- 테스트 계층:
  - **단위 테스트**: 모든 도메인 로직. 외부 I/O 없이 실행된다.
  - **통합/계약 테스트**: 모든 API 엔드포인트와 영속성 계층. 성공 경로, 검증 실패, 권한 실패,
    존재하지 않는 리소스 케이스를 각각 포함한다(MUST).
  - **E2E 테스트**: 각 사용자 스토리의 핵심 시나리오(P1 우선순위)마다 최소 1개(MUST).
- 커버리지 하한: 전체 라인 80% 이상, 도메인 모듈 라인 90% 이상·분기 85% 이상(MUST).
  커버리지가 현재 기준선보다 떨어지는 변경은 머지하지 않는다.
- 테스트는 결정적이어야 한다(MUST). 실제 시계·난수·네트워크에 의존하지 않고 주입 가능한
  대체물을 사용한다. 불안정(flaky) 테스트는 발견 즉시 수정하거나 격리하고 이슈로 추적한다.
- 테스트는 서로 독립적이며 어떤 순서로 실행해도 통과해야 한다(MUST).
- 테스트 이름은 "조건 → 기대 결과"를 서술한다(SHOULD). 구현 세부가 아니라 관찰 가능한 동작을
  검증한다.

**근거**: 손익 계산이나 사용 한도 판정의 오류는 사후에 발견하기 어렵다. 실패하는 테스트를 먼저 쓰면 요구사항이
검증 가능한 형태로 고정되고, 회귀를 머지 전에 잡을 수 있다.

### III. 사용자 경험 일관성 (UX Consistency)

- 모든 UI는 공유 디자인 토큰(색상, 간격, 타이포그래피, 반경)과 공용 컴포넌트를 사용한다(MUST).
  화면 단위로 하드코딩한 스타일 값은 금지한다.
- 같은 동작은 어디서나 같은 방식으로 보인다(MUST): 버튼 위계(주/보조/위험), 폼 검증 시점과
  메시지 위치, 확인 대화상자, 토스트 알림 위치와 지속 시간.
- 모든 데이터 화면은 로딩·빈 상태·오류·정상 네 가지 상태를 명시적으로 디자인하고 구현한다(MUST).
- 사용자에게 보이는 문자열은 메시지 카탈로그로 관리한다(MUST). 오류 메시지는 무엇이 잘못됐고
  사용자가 무엇을 할 수 있는지 알려준다. 스택 트레이스나 내부 코드를 노출하지 않는다.
- 숫자·수량·금액·날짜 표기 형식은 단일 포매터를 통해 일관되게 표시한다(MUST)
  (천 단위 구분자, 통화 기호 ₩/$, 통화별 소수 자리, 등락 부호, 날짜 형식 `YYYY-MM-DD`).
- 삭제처럼 되돌릴 수 없는 작업은 확인 단계를 거친다(MUST).
- 접근성: WCAG 2.1 AA를 충족한다(MUST). 모든 상호작용은 키보드로 가능하고, 포커스가 보이며,
  폼 컨트롤에는 레이블이 있고, 텍스트 명도 대비는 4.5:1 이상이다.
- 사용자 동작에는 100ms 이내에 시각적 피드백(눌림 상태, 스피너, 낙관적 업데이트)을 준다(MUST).

**근거**: 포트폴리오 화면은 매일 반복해서 확인하는 화면이라 사용자가 패턴을 학습해 빠르게 읽는다.
화면마다 표기와 동작이 다르면 숫자를 잘못 읽거나 잘못 입력하게 되고, 그 실수는 판단 오류로 남는다.

### IV. 성능 요구사항 (Performance Requirements)

- API 응답 시간 예산(p95, 기준 데이터셋 기준)(MUST):
  - 단건 조회: 200ms 이하
  - 목록·검색 조회: 300ms 이하
  - 생성·수정·삭제: 500ms 이하
- 프런트엔드 예산(MUST): LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하.
  초기 로드 JavaScript는 gzip 기준 200KB 이하.
- 기준 데이터셋은 계좌 2개, 보유 종목 20건(제품 상한), 가이드 기록 10,000건 이상으로 정의하고, 성능
  테스트는 이 데이터셋에서 실행한다(MUST).
- 목록 API는 페이지네이션을 기본으로 한다(MUST). 한 번에 반환하는 항목은 최대 100건이다.
  상한 없는 전체 조회 엔드포인트는 금지한다.
- N+1 쿼리는 금지한다(MUST). 조회 조건과 정렬에 쓰이는 컬럼에는 인덱스를 둔다.
- 성능 예산은 자동화된 테스트로 검증한다(MUST). 예산을 넘거나 기준선 대비 20% 이상 느려지는
  변경은 머지하지 않는다.
- 최적화는 측정 결과에 근거해 진행한다(SHOULD). 측정 없는 추측성 최적화로 코드 복잡도를
  높이지 않는다.

**근거**: 가이드 기록과 시세 데이터는 시간이 지날수록 누적된다. 처음부터 예산과 기준 데이터셋을 정해 두지
않으면 성능 저하가 서서히 쌓여 발견이 늦어진다.

## 품질 게이트 (Quality Gates)

모든 PR은 머지 전에 다음 게이트를 CI에서 통과해야 한다. 하나라도 실패하면 머지할 수 없다.

1. **정적 검사**: 린트·포맷·타입 검사 경고 0건 (원칙 I)
2. **테스트**: 단위·통합·E2E 전체 통과, 커버리지 하한 충족 및 기준선 비하락 (원칙 II)
3. **접근성**: 변경된 화면에 대한 자동 접근성 검사 위반 0건 (원칙 III)
4. **성능**: API 지연 예산, 번들 크기 예산, 기준선 대비 회귀 20% 미만 (원칙 IV)
5. **보안**: 의존성 취약점 검사에서 High/Critical 0건, 비밀정보 커밋 0건

게이트 우회는 Governance의 예외 절차를 따른다.

## 개발 워크플로 (Development Workflow)

- 기능 작업은 Spec Kit 흐름(`specify → clarify → plan → tasks → implement`)을 따른다.
  `plan.md`의 Constitution Check는 네 원칙 각각에 대한 준수 여부를 명시해야 한다(MUST).
- 모든 변경은 기능 브랜치와 PR로 진행하며, 작성자 외 최소 1명의 리뷰 승인이 필요하다(MUST).
- 리뷰어는 기능 동작뿐 아니라 이 헌법의 원칙 준수 여부를 확인한다(MUST). UI 변경 PR에는
  변경 전후 스크린샷을 첨부한다(SHOULD).
- 커밋 메시지는 Conventional Commits 형식(`feat:`, `fix:`, `refactor:`, `test:`, `docs:` 등)을
  따른다(SHOULD).
- PR은 하나의 목적만 담는다(SHOULD). 리팩터링과 기능 변경은 분리한다.

## Governance

- 이 헌법은 다른 모든 개발 관행과 가이드보다 우선한다. 충돌 시 헌법을 따른다.
- **개정 절차**: 개정은 PR로 제안하며 변경 사유, 영향 범위, 필요한 마이그레이션 계획을 포함한다.
  메인테이너 승인 후 머지하고, 같은 PR에서 버전과 `Last Amended` 날짜를 갱신한다.
- **버전 정책**(Semantic Versioning):
  - MAJOR: 원칙 삭제, 또는 기존 원칙을 호환되지 않게 재정의
  - MINOR: 원칙·섹션 추가, 또는 지침의 실질적 확장
  - PATCH: 문구 명확화, 오탈자 수정 등 의미 변화 없는 수정
- **예외 절차**: 원칙이나 게이트를 지킬 수 없는 경우 `plan.md`의 Complexity Tracking 표 또는
  PR 설명에 위반 항목, 사유, 더 단순한 대안을 택하지 않은 이유, 해소 계획을 기록하고 리뷰어의
  명시적 승인을 받는다(MUST). 승인 없는 예외는 허용하지 않는다.
- **준수 점검**: 모든 PR 리뷰에서 원칙 준수를 확인하고, 분기마다 수치 기준(복잡도, 커버리지,
  성능 예산)이 프로젝트 현실에 맞는지 재검토한다.
